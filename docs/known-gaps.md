# Known gaps

## Must implement now

Problems that are already live (not hypothetical future ones) and affect how the app behaves today.

- **With the Next.js frontend, the client IP is the Next.js server's, even without a load balancer.** The frontend renders on the server and calls this API from its Node server, so for those calls `req.ip` is the Next.js server's address, not the user's. Every user then shares one counter per route: `login` allows 10 per minute for the whole site, so the 11th login by anyone in that minute gets a `429`, and anyone can use up that shared allowance (by submitting wrong passwords through the normal login form) and block every other user from logging in. The per-IP limits in `auth.controller.ts` therefore don't protect anything until this is fixed, since they can't tell users apart, and an IP recorded for any security purpose (the future audit log, see the structured logging item under **Auth / OAuth**) would be the Next.js server's as well. The first paragraph under **Problem 1** in **Deployment / rate limiting** ("everyone shares one counter") applies today, not only once a proxy is added. The real client IP is only available to the Next.js server (from its own request headers), so it has to be passed on to this API and trusted there, and only when the request really comes from the Next.js server: trusting a forwarded IP from anyone would let a caller who reaches the API directly pick its own IP and dodge every limit. Nothing does any of this yet. The Google routes are the exception, because the user's browser calls them directly. Because the per-IP limits are this weak, the per-account protections in the credential stuffing item under **Auth / OAuth** matter more.

## Testing

- **Zero test coverage for the auth flow.** `src/health/health.controller.spec.ts` is the only non-auth unit test in the repo. Nothing exercises `signup`, `login`, `logout`, `logout-all`, `refresh`, `forgot-password`, `reset-password` or `change-password` — not the happy paths, not the error branches (invalid credentials, expired/reused/superseded tokens, rate limiting, etc.). This is the single highest-value thing to add next. The only auth-related unit test is `src/auth/refresh-replay.crypto.spec.ts` (the seal/open helper behind the refresh replay window); nothing yet exercises `refresh()` itself, so these have no automated test: replay inside the window returns the identical refresh token, replay after the window revokes everything, replay after the replacement was used or after `logout`/`logout-all`/reset/password change revokes everything, and two parallel refreshes both succeed with one new row (an e2e case that needs migrations to run in CI). Cases that guard past fixes and deserve a test first: `login` doing the same hashing work for unknown, password-less and wrong-password accounts; `logout` with a valid token id but a wrong secret changing nothing; `reset-password` giving the same error for a valid id with a wrong secret regardless of the password sent; `forgot-password`'s 60 s cooldown and constant response time (use fake timers); a concurrent `refresh` + `reset-password` / `change-password` / `logout-all` leaving no active refresh token behind (the user-row lock); `change-password` accepting the token it issues in the same second (`iat` granularity) and rejecting older ones; and the JWT `iss`/`aud`/algorithm checks.
- **The email verification (OTP) flow has no automated tests.** Nothing covers `EmailVerificationService` (`issue`, `verify`'s attempt cap / expiry / concurrent-claim / transaction, `resend`'s cooldown and mail-failure handling) or `EmailVerifiedGuard` (public, `@AllowUnverified()`, unverified, verified).
- No e2e tests beyond `test/health.e2e-spec.ts` either.
- **The Google OAuth flow is only manually verified** (real browser login, plus throwaway scratch probes). Nothing automated covers `AuthService.findOrCreateOAuthUser` (the linking rules and the concurrent-first-login recovery), `exchangeOAuthLoginToken`, `GoogleAuthGuard`'s `state` check, or `OAuthCallbackExceptionFilter`.

## Auth / OAuth

- **A completed password reset doesn't mark the email verified.** The reset link proves control of the inbox, so `resetPassword` could set `emailVerified = true` in its existing transaction (safe: it also replaces any password an attacker chose at signup). Today only the OTP does; a user who resets their password still has to enter a code.
- **An unverified, never-verified password account "squats" its email**: it blocks the real owner from signing in with Google (they get `email_already_in_use`) until it's verified or removed. Verification makes it *possible* to clear this, but nothing expires stale unverified accounts yet. Consider deleting them after some days; the owner can already recover through *forgot password*.
- **Email verification: throttling is per IP, not per user.** `verify-email` (5/min) and `resend-verification` (3/15 min) use the default IP tracker. The per-code attempt cap (5) and the 60 s resend cooldown are the real per-user limits. A per-user throttler tracker would be tighter.
- **Email verification: small edge cases left as-is.** (1) Two simultaneous `resend` calls can both pass the cooldown check and send two emails (the second code invalidates the first, so it isn't a security issue). The same race can overshoot the 10-codes-per-24-hours cap by a code or two, since the count and the insert aren't atomic; it can't be exploited for more than a handful of extra guesses. (2) If the email provider fails on `resend`, the code row is already saved, so the 60 s cooldown still applies to the retry.
- **Pre-existing password accounts are all unverified** (they predate the feature). They can log in but are confined to `verify-email`, `resend-verification` and `me` until they verify. Nothing backfills or notifies them.
- **The Google OAuth flow does not use PKCE (review item I14).** The authorization request carries no `code_challenge` and the code exchange sends no `code_verifier`, so a stolen one-time `code` is protected only by the client secret (which stays on the server) and by the `state` cookie (which stops login CSRF). That is sound for a confidential client, which is why it isn't urgent, but current OAuth guidance (RFC 9700; required in OAuth 2.1) recommends PKCE for every client as defence in depth, because it ties the code to the browser session that started the flow. Passport's Google strategy normally keeps the PKCE verifier in a server-side session, and this API is stateless (`PassportModule.register({ session: false })`, no session store), so adding it means giving the strategy another way to remember the verifier between the start and the callback.
- **`GET /auth/google` (the start route) returns a plain JSON `429`** when rate-limited, because only the callback route has the redirecting `OAuthCallbackExceptionFilter`. Only reachable by hammering the route.
- **A password reset can set the same password the account already has.** `resetPassword` used to reject this with "New password must be different from your current password", but that check ran before the token was validated and acted as a password oracle (anyone with just a reset-token ID could test guesses of the current password). It was removed on purpose. Harmless in practice (the reset still revokes all sessions and invalidates access tokens), but if the "must differ" rule is ever wanted back, it has to run only *after* the token's hash, expiry and used/invalidated state are verified, and before the atomic claim would burn the token.
- **Account enumeration is deliberately still possible through `signup` (and Google OAuth).** `signup` returns `409 Email already exists` for a taken email, and the OAuth callback redirects with `email_already_in_use` for the same situation, so anyone can test whether an address has an account. `login` and `forgot-password` no longer leak this (`login` runs exactly one argon2 verify on every failure path, against a dummy hash when the user is missing or password-less; `forgot-password` holds every response until a fixed minimum time has passed, so the time doesn't depend on whether the user exists. That minimum in `AuthService.forgotPassword` must stay above the worst realistic duration of the known-email path (DB transaction plus the mail provider call), otherwise the leak comes back for slow requests). Hiding it on signup would mean always answering "check your email" and mailing either a verification code or an "you already have an account" notice, which also means signup can no longer return tokens immediately, i.e. a redesign of the API and the clients. Accepted as a trade-off for now; revisit if enumeration becomes a real concern. Timing fixes only reduce the signal, they don't eliminate it, so keep the rate limits (see the rate-limiting note below) in place.
- **Expired and used auth rows are never cleaned up.** Nothing deletes old rows from `refresh_tokens`, `reset_tokens`, `oauth_login_tokens` or the email verification codes table, so they grow forever (there's no `@nestjs/schedule` or any cron job in the app). Harmless for correctness, but they bloat the tables and indexes over time. Options: add `@nestjs/schedule` with a daily job that deletes rows that expired (or were revoked/used/invalidated) more than N days ago; or run the delete as a scheduled ECS task / database job instead. Note that with several ECS tasks an in-app cron runs once per task: deletes are idempotent so it's safe, just redundant. Keep recently revoked refresh rows for a while, since reuse detection (`refresh` seeing a revoked token) depends on them still existing. The job should also set `refresh_tokens.replacementCipher` to NULL once the replay window has passed (an encrypted copy of a refresh token has no reason to outlive it), even for rows it keeps.
- **`forgot-password` cooldown has a small race.** `forgotPassword` skips creating and sending a reset link if one was created for that user in the last 60 s (`PASSWORD_RESET_COOLDOWN_MS`). The check and the insert aren't atomic, so two simultaneous requests can both pass it and send two emails; the second token invalidates the first, so it isn't a security issue (same edge case as the OTP `resend`). It could be closed by doing the check inside the transaction after locking the user row (`pessimistic_write`). Also note a user who didn't receive the first email has to wait the 60 s, so the frontend should say so. The plain reset token is never stored (only its SHA-256 hash), so a skipped request can't resend the earlier link. The same race applies to the 10-reset-emails-per-24-hours cap (the count and the insert aren't atomic), so it can overshoot by a link or two under concurrent requests; locking the user row would close both. That cap is silent on purpose (no `429`, so existence isn't revealed), and it has the usual unauthenticated-cap downside: someone can use up another person's allowance and block their password reset until old links age out of the 24-hour window.
- **`signup` is only limited per IP, so the mail relay risk is reduced, not removed.** It allows 10 signups per hour per IP, each of which emails a code to whatever address was submitted. An attacker with many IP addresses can still mail many *different* addresses (one email each: a repeated address answers `409`). Nothing yet caps total outbound mail across all users; options are a global brake (count `email_verification_codes` created in the last hour across all users, and skip the send past a threshold, which works across ECS tasks without Redis), alerts and quotas on the Brevo side, and CAPTCHA/Turnstile on signup and forgot-password (the widget is frontend, but the token must be verified by the backend, which also means a new required env var with the usual Joi/CI/ECS steps). Decided to defer CAPTCHA until abuse shows up or a public launch is near.
- **Next feature: let Google-only users set a first password while logged in.** A user who signed up with Google has `passwordHash = NULL`. Today the only way to add a password is *forgot password → reset password* (email link), and `POST /auth/change-password` rejects them with `400` because there's no current password to check. A dedicated authenticated endpoint (e.g. `POST /auth/set-password`) would be a better experience. Things to decide when building it:
  - **Proof of identity.** There's no current password to verify, so a stolen access token alone could otherwise be used to set a password and take over the account permanently. Require something fresh: an emailed code or link confirmation (reuse the OTP machinery), or a recent Google re-login. The forgot-password flow already proves inbox control, which is why it's acceptable today.
  - **Rules.** Strict default access tier (verified email). Only allowed while `passwordHash IS NULL` (a user who already has a password uses `change-password`). Same length limits as everywhere (`PASSWORD_MIN_LENGTH`/`PASSWORD_MAX_LENGTH` in `src/auth/auth.constants.ts`), a throttle constant next to the others, and the claim-then-act pattern if a single-use confirmation token is involved.
  - **Sessions.** Treat it like the other credential changes: set `passwordChangedAt`, revoke the other sessions' refresh tokens and re-issue a pair to the calling device, in one transaction that updates the `users` row first (the same lock order as `refresh`, `change-password` and `logout-all`; see `CLAUDE.md`).
  - **Docs and API.** Add the endpoint and its errors to the README, point the `change-password` `400` message and the "Accounts can have no password" note at it, and consider exposing a `hasPassword` flag (e.g. on `GET /auth/me`) so the frontend knows whether to show "change password" or "set password". Exposing it tells the client which sign-in method the account uses, which is fine for the account's own owner.
- **Reuse detection can't tell a thief from a stale device, and the response is now instant.** `change-password`, `reset-password` and `logout-all` revoke every refresh token, so any *other* device the user still has open holds a revoked token. When that device next calls `/auth/refresh`, the backend sees a revoked token (one that was not rotated, so the replay window doesn't apply), assumes compromise and runs `logoutAll()` again, which now also kills the access tokens of whatever session the user has just created (including the device that changed the password). Before, only the refresh tokens died, so the new session survived until its access token expired. The user has to log in once more. It's the safe direction and matches "assume compromise", but if it becomes a support problem, the fix is to tell "revoked by a bulk logout" apart from "rotated/used" (e.g. a `revokedReason` column) and only treat the latter as reuse.
- **Password-less users can't be told apart in the API**: `login` returns the generic `401` for them by design, so the frontend can't suggest "you signed up with Google". Revisit if that becomes a UX problem (it would need an intentional account-enumeration trade-off).
- **There is no structured security logging (review item I10).** Security-relevant events are not recorded in any consistent, queryable form: successful and failed logins, signups, password resets and changes, `logout-all`, refresh-token and reset-token reuse detections, refresh replays served inside the replay window, OTP attempt exhaustion, OAuth account linking and email verification. The only logging is a few free-text `Logger` lines (mail failures, the OAuth state check, the OAuth callback filter). Nothing records who (user id), from where (IP, user agent) or when in fixed fields, so a reuse detection firing in production would go unnoticed and there is nothing to reconstruct an incident from or to alert on. Note that `req.ip` is the Next.js server's address (and would be a proxy's behind a load balancer), not the client's, until the client-IP problem under **Must implement now** and the `trust proxy` gap under **Deployment / rate limiting** are fixed.
- **No per-account protection against credential stuffing and distributed guessing (review item I11).** `login` is limited per IP only (10/min), and nothing counts failed attempts per account or per email. An attacker spreading attempts over many IP addresses stays under the per-IP limit on every one of them, so a single account can be guessed at without bound, and one common password can be sprayed across many accounts. The per-IP counters are also in-memory and per task, which weakens the limit further (see **Deployment / rate limiting**). Separately, **there is no breached-password check**: signup, `reset-password` and `change-password` only enforce the length limits (`PASSWORD_MIN_LENGTH`/`PASSWORD_MAX_LENGTH`), so passwords that are already public in leaks are accepted, which is what makes credential stuffing succeed.

## Frontend dependencies

- **The Next.js server should still de-duplicate token refreshes, but a mistake is no longer fatal.** `AuthService.refresh()` now has a 20-second replay window (`REFRESH_TOKEN_REPLAY_WINDOW_TTL`): the first request atomically claims the refresh token (sets `revokedAt` and `replacedAt`) and issues a new pair; a later request presenting that same token inside the window gets the **same new refresh token** back (stored encrypted, see `CLAUDE.md`, "Refresh replay window") and a fresh access token. A replay *outside* the window, or of a token revoked by anything other than rotation, still **revokes all of the user's sessions** ("assume compromise"). The frontend is a server-rendered Next.js app that keeps the refresh token in a cookie, so the refresh is made by the Next.js server, and several requests can arrive there at once carrying the same cookie (parallel requests, several tabs, a retry after a lost response). Those are now harmless as long as they arrive within 20 seconds of the first.
  - **What the Next.js app should do:** de-duplicate concurrent refreshes for the same refresh token so only one call reaches the API (saves requests and rate-limit budget), and always write the refresh token from the response into the cookie. Retrying `/auth/refresh` with the old token after a lost response is safe only within 20 seconds of the original request; after that it is a reuse and revokes every session. De-duplicating inside one Node process doesn't cover several Next.js instances, which is exactly what the server-side window covers.
  - **How the window was built (and what it costs):** `refresh_tokens` has three nullable columns, `replacedAt`, `replacementId` and `replacementCipher`. The cipher is the new refresh token encrypted under a key derived from the old token's secret, so the database never holds a readable token and only a holder of the old token can open it. The costs are accepted deliberately:
    - **Inside the window a replay is not detected.** A thief who holds the old token and presents it within 20 seconds of the real user's rotation receives a working copy of the user's *new* pair, not a rejection. They share one session with the user instead of being flagged. Detection resumes afterwards: as soon as either party rotates the new token, the other one's next use is a reuse and ends every session. A thief who simply wins the race instead is also unchanged from before.
    - **A rotated token, then `logout` of the new one, then a replay of the old one within 20 seconds** is treated as reuse and runs `logoutAll()`. That is the safe direction, but it can look like a surprise logout on every device.
    - **The window is a constant, not an env var,** and is compared against `Date.now()` of whichever ECS task serves the replay, so clock skew between tasks shifts the effective window by that skew. Irrelevant at 20 seconds.
    - **No log line when a replay is served yet,** so you can't see how often it happens. Add it as part of the structured security logging item below.

## Deployment / rate limiting

- **Rate limiting will break as soon as a proxy/load balancer is put in front of the app, and is only approximate with more than one task.** Apart from the Next.js client-IP problem (see **Must implement now** at the top), the counting itself is fine today (the app is exposed directly, and there is a single task), but it must be fixed at the same time as either change below.

  **How it works now.** `ThrottlerGuard` (`src/app.module.ts`) counts requests per key, where the key is the route plus the client's `req.ip`. Counts live in `@nestjs/throttler`'s default in-memory store, i.e. a plain map inside the Node process. `main.ts` does not set `trust proxy`, so `req.ip` is the address of whoever opened the TCP connection to Node. With no proxy in front and a browser calling the API directly, that is the real client, so every IP gets its own counter. Calls made by the Next.js server are the exception (see **Must implement now** at the top).

  **Problem 1: adding an ALB / CloudFront / nginx / any reverse proxy.** Every request then reaches Node from the proxy's own (private) IP. All users share one counter per route, e.g. 10 logins per minute for the whole world, so a few users can lock everyone out of `login`. The real client IP is in the `X-Forwarded-For` header the proxy adds, but Express ignores it unless told to trust it.
  - **Fix:** in `src/main.ts`, create the app as `NestFactory.create<NestExpressApplication>(AppModule)` (import from `@nestjs/platform-express`) and call `app.set('trust proxy', <hops>)`. `<hops>` is the number of proxies between the client and Node: `1` for an ALB directly in front, `2` for CloudFront then ALB. Do **not** use `true`, and do **not** set it while there is no proxy: the client could then send a forged `X-Forwarded-For` and pick its own IP to dodge the limit. If the hop count differs per environment, make it an env var, which means adding it to the Joi schema in `src/config/env.validation.ts` and to `ci.yml`'s `e2e-tests` env block (plus the GitHub Actions secret/variable).
  - **Verify after deploying:** log `req.ip` from two different networks; you should see two different client IPs, not the proxy's private `10.x` address.

  **Problem 2: running more than one ECS task.** Each task has its own in-memory map, and the load balancer spreads a client's requests across tasks, so the effective limit is roughly `limit x number of tasks` (5 logins/min becomes about 10 with 2 tasks). Limits still work per IP, just loosely.
  - **Fix:** move the counters to a shared store all tasks read and write, i.e. Redis (e.g. ElastiCache). Install a throttler Redis storage package (`@nest-lab/throttler-storage-redis` or `nestjs-throttler-storage-redis`) and pass it as `storage` to `ThrottlerModule.forRoot(...)` in `src/app.module.ts`. This needs a Redis instance and a new env var (e.g. `REDIS_URL`), with the same Joi and CI requirements as any new env var.

  Note that with multiple tasks you will almost certainly also have a load balancer, so in practice both fixes land together.
- **Redis is not part of the stack yet, and nothing today strictly requires it.** The only current uses for it are (1) shared storage for the throttler counters once there is more than one ECS task (Problem 2 above), and (2) per-email login failure counters (see the credential stuffing item under **Auth / OAuth**). Everything else is already served by Postgres: the per-account daily caps and cooldowns for password-reset emails and verification codes, and token/session invalidation (`passwordChangedAt`, `tokensValidAfter`). The app has no caching, queueing or domain workload that would need it. Adding it means an ElastiCache instance, a service in `docker-compose.dev.yml`, and a new required `REDIS_URL` with the usual Joi, `ci.yml`, GitHub Settings and ECS task definition steps.
- **The client IP seen by this API is the Next.js server's.** This is already a live problem; it is described under **Must implement now** at the top of this file.
- **The per-route limits in `auth.controller.ts` (10/hour for signup, 10/min for login, 3 per 15 min for forgot-password, 20/min for refresh, reset-password, oauth/exchange and the Google routes, etc.) and the app-wide default of 300/min in `app.module.ts` were chosen assuming per-IP counters** and should be re-checked once the fixes above are in, since people behind the same NAT (offices, mobile carriers) share an IP.
- **`GET /auth/me` is capped at 20/min per IP** like the other auth routes. A frontend that calls it on every page load, or several users behind one NAT, could hit that; give it its own higher constant if that happens.

## Infrastructure, CI/CD and Docker

Everything about the pipeline, the container image and the AWS side that is unfinished, unverified or needs a decision. Items under "Before the next deploy" are one-time setup that the repo can't do for itself; the rest are gaps to revisit.

### Before the next deploy to `main` (needs a person with AWS/GitHub access)

The deploy now runs database migrations as a one-off ECS task before the service is updated (`cd.yml`, step "Run database migrations"). None of the AWS side has been exercised yet, so:

- [ ] **GitHub variables.** Add `ECS_SUBNETS` (comma-separated subnet ids) and `ECS_SECURITY_GROUPS` (comma-separated). Copy them from the ECS service's networking tab so the migration task runs in the same network as the app (it must reach the database).
- [ ] **IAM.** The role in the `AWS_ROLE_ARN` secret needs `ecs:RunTask`, `ecs:DescribeTasks` and `iam:PassRole` (for the task's execution role and task role), on top of what it already has.
- [ ] **Launch type.** The step hardcodes `--launch-type FARGATE`. Change it if the service runs on EC2.
- [ ] **ECS task definition env vars.** The deploy downloads the *live* task definition from AWS, so env vars come from AWS, not this repo. Check that all 19 keys required by `src/config/env.validation.ts` are present (especially `EMAIL_VERIFICATION_TTL`, `OAUTH_LOGIN_TOKEN_TTL` and the three `GOOGLE_*`). A missing key makes the container fail env validation at boot, and the migration task would fail the same way.
- [ ] **Open a PR to `main` and wait for CI to go green** before merging (CI runs only on pull requests; CD runs only on pushes to `main`).
- [ ] **Watch the first deploy.** The migration step has never run against real AWS. If it fails, the deploy stops before the service is touched; the migration task's own output is in the container's CloudWatch log group, not in the Actions log.

### Known gaps

- The `docker-build` job's container smoke test (`.github/workflows/ci.yml`) still soft-fails on purpose — it doesn't provision a Postgres service or pass any env vars to `docker run`, so the container can't actually boot inside that job yet. To make the health-check curl a real (hard-failing) check, that job needs the same `postgres:` service + full env var set that `e2e-tests` already has.
- `docker-compose.yml` has the same limitation: it passes no env vars and has no database, so the app fails env validation at boot and the container never becomes healthy (its healthcheck now correctly hits `/health`). Add `env_file: .env` and a database (see `docker-compose.dev.yml`), or treat the file as build-only.
- **Migrations run against the live database while the old code is still serving.** Only additive migrations (new nullable columns or tables, new indexes) are safe; a rename or drop breaks the running version until the new one is up. There are also no automated rollbacks: if the migration succeeds but the service deploy then fails, the schema stays ahead of the code (ECS rolls the code back, not the database). Write `down()` methods and keep migrations backwards compatible.
- **The migration step is hard to debug and slightly misleading when it fails.** The Actions log shows only the exit code (the output is in CloudWatch). `run-task` failures (no capacity, bad subnet) surface as a cryptic `None` ARN error. The "Deployment failure" summary at the end always says "ECS service did not stabilize", even when the migration step was what failed.
- **Every deploy registers two identical task definition revisions** (once in the migration step, once in the deploy action). Harmless, but the revision list grows twice as fast. If it ever becomes noise, register once and pass the same ARN to both steps.
- **Graceful shutdown is in place (`app.enableShutdownHooks()` in `src/main.ts`), but only partly verified.** On a deploy ECS sends SIGTERM (forwarded to Node by `tini`; the Dockerfile's `CMD` runs `node` directly, not through `pnpm`, so the signal arrives). Nest now stops accepting connections, lets in-flight requests finish, closes the TypeORM pool and exits. Before this, Node died immediately and could cut off an `/auth/refresh` after it committed the rotation, so the Next.js server never got the new tokens, retried with the old one and triggered the replay response (revoke **all** sessions, see **Frontend dependencies**). What is still open:
  - **It has not been checked against the real ECS service.** The task's stop timeout must stay above the slowest route (`forgot-password` takes at least 3 s, `FORGOT_PASSWORD_MIN_MS`, plus up to 2 s for the mail call); ECS defaults to 30 s, which is enough, but confirm nobody lowered it. If it is shorter than a request, ECS sends SIGKILL and the old behaviour is back. The load balancer's deregistration delay (default 300 s) and whether tasks are replaced during deploys are also unverified.
  - **It only covers deploys.** A crash, an OOM kill or a lost network response between the API and the Next.js server can still lose a committed rotation. The replay window (see **Frontend dependencies**) now recovers that, but only if the retry arrives within 20 seconds.
  - **A long-lived keep-alive connection can delay shutdown** until the stop timeout. Node closes idle connections on `server.close()`, so it is unlikely to matter, but it is untested.
- **A vulnerable image is already in ECR when the scan runs.** `build-and-push` pushes `:sha-…` *and* `:latest` before `image-scan`. The scan now fails the pipeline (so it isn't deployed), but the bad image stays in the registry and `:latest` points at it. Consider scanning before pushing `:latest`, or tagging `:latest` only after the scan passes. There is also no `.trivyignore`, so an unfixable false positive would block deploys until the base image changes.
- **SHA-pinned actions will go stale.** All actions are pinned to commit SHAs (good), but there is no Dependabot/Renovate config to propose updates, so security fixes in the actions themselves will not arrive on their own. `configure-aws-credentials` is on `v4.3.1`; `v6.x` exists.
- **The Docker build isn't fully reproducible.** The base image is a floating tag (`node:24-alpine`, not a digest), and the Dockerfile runs `apk upgrade` and `npm install -g npm@latest` (a Trivy CVE workaround), so two builds of the same commit can differ.
- **CI and CD e2e jobs use the real repo secrets** (`JWT_SECRET`, `BREVO_API_KEY`, `GOOGLE_OAUTH_CLIENT_SECRET`) and vars. Throwaway values would be safer (the e2e suite never needs to send real email or talk to Google), and pull requests from forks get no secrets, so their e2e job fails at env validation.
- **E2E jobs don't run migrations.** `test/health.e2e-spec.ts` only needs a connection, so it passes. The first e2e test that touches a table will fail until the job runs `pnpm run migration:run` (against the CI Postgres) before `pnpm test:e2e`.
- **`pnpm audit --audit-level=high` blocks every PR** when a new advisory appears in any dependency, whether or not the PR touched dependencies. Expected, but be ready to add an `overrides` entry (as `pnpm-workspace.yaml` already has) or pin around it.
- **The pnpm version lives only in `package.json`'s `packageManager`.** `pnpm/action-setup` must not get a `version:` input again (it errors when pnpm is specified twice), and anyone with a different local pnpm gets it switched automatically for this repo. Bumping pnpm means changing that one field and checking `pnpm install --frozen-lockfile` still passes.
